# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

The repository root is the workspace; it is one git repository (GitHub `Crow08/PortalSync`) with two projects that together form one application (synchronized group listening/watching of music and video):

- `server/` — Spring Boot 4.1 (Spring 7, Jakarta EE 11, Jackson 3, Hibernate 7; Java 27 (Liberica Full 27 in `~/.jdks`, IntelliJ project SDK `liberica-full-27`), Maven, packaged as `war`), package `de.crow08.portalsync`
- `tools/` — PowerShell helpers that are not part of the build: `convert-video.ps1` (ffmpeg conversion, thumbnail sprites) and `start-caddy.ps1` (Caddy TLS proxy, uses `Caddyfile` in the repository root)
- `client/` — Angular 22 + Angular Material SPA, STOMP over WebSocket via `@stomp/rx-stomp` (own `RxStompService` in `services/rx-stomp.service.ts`)

Commit from the repository root; a change to the WebSocket protocol belongs into one commit touching both projects. `data.sql` (local seed) and `.idea/`, `.claude/` are git-ignored.

- Build: `mvn package` (produces `target/portalsync-server.war`)
- Run: `mvn spring-boot:run` — active profile defaults to `dev` (`application.properties`); override with `-Dspring-boot.run.profiles=prod`. `mvn package` builds an executable war (`java -jar target/portalsync-server.war`, `spring-boot-maven-plugin`), which still deploys to an external Tomcat.
- Shared IntelliJ run configurations (`.idea/runConfigurations`, the rest of `.idea` is git-ignored): "Client dev" (`npm start`), "Server dev" (Maven `spring-boot:run`, profile `dev`; the developer's own `Server_dev.xml` with `SPOTIFY_CLIENT_ID`/`SPOTIFY_CLIENT_SECRET` as Maven runner environment variables is git-ignored, the secret-free template is `Server_dev.xml.example`, the credentials are optional) and "Docker up"/"Docker down" (`docker compose --profile tls up -d --build`/`down` in the repository root, needs a `.env`; the `tls` profile binds ports 80 and 443; "Docker up" first runs `npm run buildServer` in the client and stops if that fails, which only refreshes the local `static/`: the image builds the client itself). The Maven run configuration needs the project SDK (`liberica-full-27`) in IntelliJ. IntelliJ keeps its own copy of the Maven model: after a `pom.xml` change it has to reload the Maven projects, otherwise its build fails on the old classpath.
- Requires a MySQL/MariaDB database `music_stream_server` on `${MYSQL_HOST:localhost}:3306` and env `SPOTIFY_CLIENT_ID`. The local database is the XAMPP MariaDB 10.4.6. Hibernate 7 officially needs MySQL 8 / MariaDB 10.6+ and logs `HHH000511` ("5.5.5 version ... no longer supported") at every start; it works with the default `MySQLDialect`. `MariaDBDialect` does **not** work on 10.4 (`alter table if exists` is a syntax error). With `ddl-auto=update` on an existing schema, every start logs about 60 `GenerationTarget encountered exception ... Error executing DDL "alter table ... add constraint FK..."` warnings (errno 121, duplicate key): Hibernate cannot see the existing foreign keys on this old server and tries to add them again. They are harmless, the constraints exist; do not "fix" them by dropping tables.
- Unit tests: `mvn test` (JUnit 5, AssertJ; `src/test`). They cover the rules of the sessions without Spring or a database: `QueueTest` (next/previous/skip, moving, finding by id, fair order, the version), `SessionTest` (states, timing with fixed times, sync rounds) `SessionRepositoryTest` (ids of sessions created at the same time) and `CommandJsonTest` (the JSON fields of the WebSocket commands, which the client mirrors as types). Repositories and Spring collaborators are Mockito mocks, requests `MockHttpServletRequest`; no test starts Spring or needs a database. Mockito runs as a Java agent (`pom.xml`: the dependency plugin's `properties` goal and the `argLine` of surefire), because newer JDKs warn about and will forbid its attaching itself; tests started from IntelliJ do not get the agent and still print that warning. The REST controllers, the security configuration as a whole and the WebSocket handlers are covered by the client's e2e tests only. The Docker build skips the unit tests (`-DskipTests`).

## Environment / profiles

The client environment file and the server profile must match, otherwise CORS and the WebSocket `setAllowedOrigins` check fail:

| Client config (`src/environments/`) | Server profile | Backend port |
|---|---|---|
| `environment.development.ts` (`development` configuration, `npm start`) | `dev` | 8081 |
| `environment.ts` (default, production builds, also the Docker image) | `prod` | 8080 (behind the TLS proxy: `https://`/`wss://` on 443) |

There is no `preprod` profile or client configuration any more (`environment.preprod.ts`, `application-preprod.properties`, the `preProd` configurations in `angular.json` and the `startPreProd` script are gone).

Server-side, `client.origin` (`prod`) or `client.host`/`client.port` (`dev`) define the single allowed origin (used in both `SecurityConfig.addCorsMappings` and `WebSocketConfig`). `client.storage-path` (`F:/media/` in `dev`, `MEDIA_PATH` in `prod`, **must end with a slash**) is the filesystem root of the media files.

`dev` and `prod` both use `ddl-auto=update` on a persistent database (`dev`: `music_stream_server` on the local XAMPP, `MYSQL_DATABASE` overrides it; `prod`: `portalsync`): **nothing is wiped on start and `data.sql` is not run automatically** (`spring.sql.init.mode` is not set). Never drop the database to "reset" it; it holds the real library. `src/main/resources/data.sql` is only a local seed for an *empty* database (users 1–5, media 1–29, playlists 1–4, user 1 `admin`). It is **git-ignored** (real user names and password hashes, personal library) and not in a fresh clone; the README describes creating the first admin by SQL. If it exists, load it by hand, e.g. `C:\xampp\mysql\bin\mysql.exe -u root --default-character-set=utf8mb4 music_stream_server -e "source src/main/resources/data.sql"` after the server created the tables. Hibernate has to create the schema first; `playlist_owner` stays empty until the next server start (`PlaylistOwnerMigration` makes the authors the owners). In the seed, playlist 4 ("Bleach", media 1–29) references files under `F:/media/videos/`; other media may not exist.

`src/main/resources/static/` contains a copy of the client build (hashed bundles) that the server serves itself (`SecurityConfig`: `ClientResourceResolver`; paths without a file extension, except `/api` and `/ws`, get `index.html` for the client router). It is not rebuilt automatically — run `npm run buildServer` in the client.

HTTPS (prod): `Caddyfile` (repository root) runs Caddy as TLS proxy for the host name in the environment variable `PORTALSYNC_DOMAIN` (required) and forwards everything to the server (`localhost:8080`, `PORTALSYNC_UPSTREAM` overrides). One origin: `environment.ts` takes `window.location.origin` for `dbServer`, `frontendServer` and `wsServer` (ws/wss derived), so the production build contains no host name and works on every domain, but only when the server serves the client itself. The `prod` profile therefore takes `client.origin` from the environment variable `CLIENT_ORIGIN` (default `http://localhost:8080`, the only origin allowed for CORS and the WebSocket; e.g. `https://portalsync.example.org`; other prod variables: `SERVER_PORT`, `MYSQL_HOST`/`MYSQL_DATABASE`/`MYSQL_USER`/`MYSQL_PASSWORD`, `MEDIA_PATH`, `URLCRYPTO_SECRET`, `SPOTIFY_*`; the Spotify redirect defaults to `CLIENT_ORIGIN/spotify/redirect`) and `server.forward-headers-strategy=framework` (Spring has to see `https`, otherwise the CORS check treats same-origin requests as foreign). Caddy: the single binary of the official release (https://github.com/caddyserver/caddy/releases, `caddy_<version>_windows_amd64.zip`, check the SHA-512 from the checksum file) lies in `D:\Programs\caddy\caddy.exe`, not in the project. Start it with `tools\start-caddy.ps1` (`-Detached` runs it hidden with the log in `%TEMP%\caddy.log`, `-Stop` stops it; `caddy.exe` is looked up in `CADDY_EXE`, that path and the PATH). The script stops when port 80 or 443 is in use, by any other web server. Caddy obtains and renews the certificate itself and stores it in `%APPDATA%\Caddy` (add `acme_ca https://acme-staging-v02.api.letsencrypt.org/directory` in a global block of the Caddyfile for tests: staging has no rate limits but browsers do not trust it). It does not run as a service by itself. Spotify's redirect URI has to match `spotify.client.redirect` exactly and has to be HTTPS (except loopback IPs, `localhost` is not allowed).

Docker (`compose.yaml`, `Dockerfile`, `.dockerignore`, `.env.example` in the repository root): `cp .env.example .env`, set `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD` and `URLCRYPTO_SECRET` (required, no default), then `docker compose up -d --build` in the repository root (app on `127.0.0.1:8080`, `APP_BIND`/`APP_PORT` change that; `docker compose --profile tls up -d` adds Caddy on 80/443 for `PORTALSYNC_DOMAIN`). Services: `db` (MySQL 8.4, volume `db-data`; unlike the local XAMPP MariaDB 10.4 it needs no Hibernate workarounds and logs no DDL warnings), `app` (client + server in one image with ffmpeg for the video upload, Spring profile `prod` = `application-prod.properties`, everything from the environment: `MYSQL_*`, `CLIENT_ORIGIN` = the only allowed origin, `URLCRYPTO_SECRET`, `SPOTIFY_*`, `MEDIA_PATH`) and optional `caddy`. The build context is the repository root (both projects side by side), the Dockerfile builds the client with the normal `production` configuration (`environment.ts`: everything on `window.location.origin`, so the image is independent of the host name) and replaces `static/` in the server sources with it; `.dockerignore` is an allow list. The media library is a bind mount (`MEDIA_DIR`, default `./media`, e.g. `F:/media`) at `/media`; the app runs as uid 10001 and must be able to write there (uploads). The database starts empty: users come from the invite flow or from loading `data.sql` by hand (`docker compose exec -T db mysql -u root -p... portalsync < server/src/main/resources/data.sql`); to move the existing library, `mysqldump` the XAMPP database and load it the same way. Only compose-time variables of services in a profile need defaults (`${PORTALSYNC_DOMAIN:-localhost}`), a `:?` there would break every `up`. Verified: build, healthy stack, login, signed media with range requests, thumbnails, STOMP over ws, and the `tls` profile with `localhost`.

Secrets: the Spotify client id and secret come from the environment (`SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET`, set in the IntelliJ run configuration). The committed url-crypto key (`Not#So%Secret`) and the unset DB password in `application-*.properties` are intentional development defaults; production must override them.

## Architecture

### Two communication channels
1. **REST** (`/api/**`): CRUD for the JPA entities in `model/*` (each package has `Entity`, `Repository`, `Resource` = REST controller). Client side: `services/*.service.ts`; the login is a cookie, see "Login" below. `User.password` is write only (never serialized).
2. **STOMP over WebSocket** (endpoint `/ws`): all live session/playback control. The user comes from the WebSocket handshake, an HTTP request that is logged in like every other one (login cookie): the STOMP frames carry no credentials, only the session id as CONNECT header `session` (see `WsConfigService.configParameter`). `WebSocketAuthConfig.WebSocketAuthInterceptor` registers the connection with that user (`WebSocketSessionController.registerConnection`). The client opens the WebSocket only while a user is logged in (`SessionService`): a new login needs a new handshake.

### Login
The password is sent once, to `POST /api/v1/auth/login` (`authentication/AuthResource`). The server answers with the user (id, name, admin) and a login cookie (`LoginCookie`: HttpOnly, SameSite=Strict, Secure on HTTPS, path `/`) holding a random token; the database keeps only its SHA-256 (`LoginToken`, table `login_token`). `LoginTokenFilter` (in the security filter chain, before HTTP Basic) logs every request in by that cookie with the same principal as a password login (`AuthenticatedUser`), also the WebSocket handshake. A login ends 30 days after its last use (`LoginTokenService`, extended at most once a day), with `POST /api/v1/auth/logout`, or for the other browsers of a user when the password is changed. The server keeps no HTTP session (`STATELESS`).

- CSRF: there is no CSRF token. The browser does not send a SameSite=Strict cookie with requests of other sites, and the CORS configuration rejects requests with a foreign `Origin` header (e2e: `auth.spec.ts`). The dev client (port 4200) and server (port 8081) are the same site but different origins: the client sends the cookie with `withCredentials` (`services/auth.interceptor.ts`), the server allows credentials for its one allowed origin.
- Cookies belong to a host, not to a port: the `dev` profile names its cookie `portalsync_login_dev` (`client.login-cookie`), so the dev server and a Docker stack on 127.0.0.1 do not log each other out.
- Client: `AuthenticationService` only remembers who is logged in (`localStorage['currentUser']`: id, name, admin; never the password). Whether the login still exists shows with the first request: on a 401 `authInterceptor` forgets the user and opens the login page.
- HTTP Basic still works for clients that are no browser (scripts, the e2e fixtures, also on the WebSocket handshake); the client does not use it. It checks the password with bcrypt on every request.
- The pre-signed URLs of url-crypto-kit have their own security filter chain (`psuFilterChain` of the kit, only for signed requests) and do not need the cookie.

### Media file serving
`/api/v1/media/data/{mediaId}` is a custom resource handler in `SecurityConfig.addResourceHandlers`: it looks up the `Media` entity by id and resolves its `uri` against `client.storage-path` only (Spring 7 rejects the former `classpath:/` location). These URLs are signed via neverpile `url-crypto-kit` 2.x (pre-signed URLs, `psuEnabledPathPatterns`; an authenticated `GET .../media/data/{id}?X-NPE-PSU-Duration=PT1H` returns the signed URL as plain text, see `PlayerEngineService`), so the browser `<audio>/<video>` element can load them without Basic auth headers. Seeking uses HTTP range requests on progressive MP4 (no DASH); videos need the `moov` atom at the front (fast start). New videos (e.g. MKV with ASS subtitles, 10-bit H.264) are converted with `tools/convert-video.ps1` (ffmpeg): 8-bit H.264 + AAC, subtitles burned in, fast start; `Get-Help .\tools\convert-video.ps1 -Full` for options. The script is not part of the build.

`/api/v1/media/thumbnails/{mediaId}` (same resolver, also pre-signed) serves the seek bar preview sprite of a video: `<video uri without extension>.thumbs.jpg` next to the video, written by `convert-video.ps1` (`-ThumbnailsOnly` for existing videos). Sprite format: one 160x90 tile every 2 s, 10 tiles per row, row-major; the constants are duplicated in `convert-video.ps1`, `utils/FfmpegCommands` (video upload) and `player-track.component.ts`. Thumbnails are optional: without a sprite (songs, 404) the seek bar shows no preview.

Chapters: `convert-video.ps1` keeps the source chapters in the MP4 (`-map_chapters 0`, ffmpeg writes a Nero `moov/udta/chpl` box). Browsers do not expose MP4 chapters, so `GET /api/v1/media/video/{id}/chapters` (Basic auth, `utils/Mp4ChapterReader`) parses that box and returns `[{start, title}]` (start in seconds, empty list without chapters). The seek bar shows chapter boundaries as gaps and the chapter title in the hover preview.

### Playlist ownership
A `Playlist` has a list of `owners` (table `playlist_owner`; `author` is only the creator and the first owner) and a flag `publicOwnership`. Owners and admins change the songs (`addSongToPlaylist`, `addSongsToPlaylist`, `removeSongsFromPlaylist`, upload and import into a playlist) and manage the owners (`PUT`/`DELETE /api/v1/playlists/{id}/owners/{userId}`, the last owner can not be removed) and the flag (`PUT .../public/{true|false}`); with `publicOwnership` everybody changes the songs, but only owners and admins manage owners and flag. For everyone else a playlist is read only (403). While a playlist the user may change is shown in the library, every listed row has a button that takes its media out of that playlist (also in a filtered list), next to the same action for a selection and in the detail panel; the media stays in the library. The rules live in `PlaylistAccess`, the client mirrors them in `Playlist.canEdit`/`canManage` to hide controls. `PlaylistOwnerMigration` makes the author the owner of playlists without owners at every start (existing databases). `GET /api/v1/users/all` lists id and name of all users, `GET /api/v1/playlists/{id}/media` the media of a playlist.

### Media ownership
A `Media` has one owner (`Media.ownerId`, column `owner_id`, read only in JSON): the user who uploaded or imported it. The owner and admins edit and delete it (`editSong`, `deleteSongById`, `deleteSongs`; a bulk delete with one media the user may not delete deletes nothing), everyone else gets 403; reading and playing is open to all. Media without an owner (older rows, videos inserted by SQL) are changed by admins only. The rules live in `MediaAccess`, the client mirrors them in `DatabaseBrowserComponent.canChangeMedia` to hide the buttons. The library shows the owner: its name in every row of the list (in the accent color for the own media, hidden below 720 px) and as "Owner" in the detail panel ("name (you)", or "Nobody (admins only)" without an owner). The media only carry the id, the names come from `GET /api/v1/users/all`, which the library loads once. Two "Mine" switches filter in the client: the one in the tool bar lists only the own media (`onlyOwnMedia`, together with the type filter and the search), the one next to the "Playlists" heading only the playlists the user is an owner of (`onlyOwnPlaylists`). Editing happens in the detail panel of the library: "Edit" (owner and admins) switches it into an edit mode (`DatabaseBrowserComponent.edit`, a `MediaEdit`) with the title and, for songs, artist, album and genres (`PUT /api/v1/media/editSong`), for videos series and season (`PUT /api/v1/media/editVideo`, `EditVideoRequest` with ids that the server looks up), plus tags for both; Save stores everything at once, Cancel or opening another item drops the changes, a blank title is refused (400). Series and seasons are listed and created like artists (`/api/v1/series`, `/api/v1/seasons`; pickers `app-input-series`, `app-input-season`). Deleting (`MediaDeletion`, one transaction) first takes the media out of every playlist and deletes their ratings: the database refuses to delete a media that is still referred to. `Media` has no mapping of its playlists; the playlist owns the relation (`Playlist.media`, table `media_playlist`). The table `media_playlists` in older databases is left over from a former second mapping and unused. Deleting a song also removes its file (`MediaFileRemover`, after the transaction): only for songs that are no Spotify songs, only inside the storage, and not while another media has the same uri. So the name of a deleted song is free for a new upload. The file of an uploaded video goes the same way, with its sprite (everything under `/videos/uploaded/`, see "Video upload"); the files of all other videos stay: they are put into the storage by hand. The uri of a media and the name of an uploaded file come from clients: files are only resolved through `utils/MediaFiles`, which keeps them inside `client.storage-path`.

### Covers
A media can have a picture, the cover of its album: `Media.cover` (column `cover`, nullable) is the path of an image in the storage, e.g. `/songs/<artist>/<album>/cover.jpg`; the songs of an album share one file. The path is never sent to clients and can not be set by them: the JSON only has `hasCover` (`MediaJsonTest`), and `/api/v1/media/cover/{mediaId}` (the same resolver as the media files, 404 without a cover) serves the file. It is not pre-signed: the browser loads it as an `<img>` with the login cookie, which also works from the dev client (other port, same site). The client asks only for media with `hasCover` (`utils/cover.ts: coverUrl`) and puts the image into the existing placeholders (class `cover-image`): the rows and the detail panel of the library, the stage and the transport bar of the room, the mini player; without a cover, or when the image does not load, the gradient with the icon stays. The placeholders are square (40 px in lists and bars, 170 px in the detail panel, where a video keeps its wide banner). Cover files are written by SQL only (the import of a music collection; e2e: the shared video has one, the shared songs none). Deleting a media leaves the cover file, other media may use it.

The cover of a Spotify song is not a file: `cover` holds the URL of the album picture at Spotify, and the JSON gives it as `coverUrl` (null for files), which `coverUrl()` of the client prefers. The Spotify import sends it per song (`cover`; `pickSpotifyCover` takes the smallest picture of at least 300 px), the server takes only `https://i.scdn.co/image/<id>` (`CoverUrls`, `CoverUrlsTest`: the URL comes from a client) and gives a Spotify song that exists without a cover the one of a new import. The browsers load these pictures from Spotify (third-party request, `referrerpolicy="no-referrer"`); nothing of them is stored.

### Release dates
Songs and albums have an optional release date (`Song.releaseDate`, `Album.releaseDate`, columns `release_date`): a text as exact as it is known, `1998`, `1998-10` or `1998-10-12` (`utils/ReleaseDates`, mirrored by `utils/release-date.ts` of the client; anything else is a 400). The texts sort like the dates. A song without a date of its own shows the one of its album (`releaseDateOf`): the detail panel of the library has the row "Released", the sort "Newest release" puts media without a date (and all videos) last. The edit mode of a song has the field "Release date" (`PUT /api/v1/media/editSong`) and, while the song keeps its album, "Release date of the album", which is a property of the album and saved by `PUT /api/v1/albums/{id}/releaseDate` (`{releaseDate}`, null or blank for none): an album has no owner, admins and the owners of one of its songs may set it; the fallback album "Unknown Album" (id 1) gets none. Album names are unique in the database, so two albums of the same name by different artists are one album with one date: such songs carry their own dates. The Spotify import sends the date Spotify has for the album of each track (`release_date`, by its precision a year, a month or a day) as `releaseDate`: the song gets it, an album without a date too, and a Spotify song or album that exists without a date gets it when imported again; a value that is no date is left out and does not stop the import. Uploads set no date.

### Video upload
The upload page has two modes, Songs and Videos (`UploadComponent.mode`). Videos go to `POST /api/v1/media/videoUpload` (`model/media/video/VideoUploadResource`, multipart `files` plus `data`: `seriesId`, `seasonId`, `tags`, `playlists` and the switches `preprocess`, `burnSubtitles`, `thumbnails`); every user may upload and owns what they upload. The title is the file name without its extension, the file `/videos/uploaded/<title>.mp4` (409 if it exists).

- Without `preprocess` the file is stored as it is and is in the library at once; only `.mp4` is accepted (400), and nothing checks that browsers play it (H.264/AAC, fast start).
- With `preprocess` the upload is kept in `/videos/uploaded/.incoming/<uuid>` and converted by ffmpeg in a job, the same conversion as `tools/convert-video.ps1` (`utils/FfmpegCommands`, streams chosen by `utils/VideoProbe`: default audio track, with `burnSubtitles` the default full subtitle track; the script stays for choosing tracks by hand). The video is added to the library when the job is done (`VideoRegistration`, on the job thread: no logged in user there). `client.ffmpeg-preset`/`client.ffmpeg-crf` (default `medium`/20) set the quality.
- `thumbnails` writes the sprite of the seek bar: in the same ffmpeg run as a conversion, else in a job of its own after the video is in the library.
- Jobs (`VideoJobs`): one at a time, in memory, with the progress from `ffmpeg -progress`; `GET .../videoUpload/jobs` lists those of the user (finished ones for an hour), the upload page polls it every 2 s while one is active. A failed job only says so, the reason is in the server log. A restart loses the jobs; the next start removes the sources and the empty files that kept the names (`VideoUploadResource.removeLeftovers`).
- ffmpeg and ffprobe are optional (`client.ffmpeg`, `client.ffprobe`, default: from the PATH; the Docker image installs them). `GET .../videoUpload/info` says whether they run (checked once per server start); without them the client disables both switches and the server answers 400 to them.
- The name of the source ends up in the `subtitles` filter of ffmpeg, so the server names the file and ffmpeg runs in its directory: never put the name of an uploaded file into a filter description.
- An upload is one multipart request: the limit is `spring.servlet.multipart.max-*-size` (2 GB), a proxy in front may have its own. While it runs, the page shows a bar with what is sent, the speed and the time left (songs and videos; `HttpHelperService.postWithProgress`, the numbers in `models/transfer-progress.ts`); once everything is sent it says that the server is storing the files. This is the transfer only, the conversion has its own progress in the jobs.

### Sessions (in-memory, not persisted)
`sessions/SessionRepository` is a plain `HashMap` — sessions, their `Queue` (queued + history + current media) and connected users are lost on server restart, and session ids start at 1 again. The rules live in plain classes without Spring: `Session` holds the playback state machine (`Session.SessionState`: `PLAY, STOP, PAUSE, SYNC_PLAY, SYNC_STOP, SYNC_PAUSE`), the timing (`mediaStarted`, `savedProgression`; its methods take the current time as a parameter) and the sync rounds, `model/queue/Queue` everything about the queue, history and current media. Both are not thread safe and have no setters for that state: `SessionController` takes the lock of the session (`Session.getLock()`), calls them with `Instant.now()` and does the rest (sync timeout, messages, users of the connections). Only a paused session resumes (`Session.resumePlayback`): a second resume of a playing session changes nothing. New rules go into `Session`/`Queue` with a unit test, not into the controllers.

Deleting: `DELETE /api/v1/sessions/{id}` (`SessionResource`) is allowed for the creator (`Session.creatorId`) and admins (`User.admin`, a DB-only flag, in the dev seed user 1). `SessionController.deleteSession` removes the session and broadcasts `SessionDeleted`; the client (`PlayerEngineService`) then resets locally via `SessionService.sessionDeleted` and goes to the session list.

`WebSocketSessionController` tracks which music sessions each WebSocket connection joined (via `join` or the CONNECT `session` header). A user is only removed from a session when no other connection of that user is still in it.

### Playback command protocol
- Client publishes to `/app/sessions/{sessionId}/commands/{name}[/{params}]` (`WsService.publishSessionCommand`); handlers are the `@MessageMapping` methods in `wscommunication/PlayerControlsController`.
- Each handler returns a `Command` subclass (`wscommunication/commands/`) broadcast to `/topic/sessions/{sessionId}`. The JSON `type` field (e.g. `Start`, `SetMedia`, `Join`, `Update` with sub-types `Queue`/`History`/`QueueAndHistory`/`LoopMode`) is dispatched in the client's `PlayerEngineService.processCommand`. The client declares every command as a type (`models/session-command.ts`, the union `SessionCommand`; `parseSessionCommand` ignores messages it does not know), the server test `CommandJsonTest` pins the JSON fields of every command class: a change on one side has to be made on the other.
- Commands addressing a queue entry (`skipTo`, `movedMedia`, `deleteMediaFromQueue`) send the index in the combined list (history, current, queue) plus the media id; the server picks the occurrence of the id nearest to the index (`findInHistoryAndQueue`) and rejects the command if the media is gone.
- `SetMedia` carries the complete queue and history; the client replaces its state with them instead of deriving it from the media id (media can occur several times). When the queue ends, the server stops the session and sends `Stop` with the queue and history (no current media); a plain `Stop` has neither.
- Fair queue: the queue and history hold `QueueEntry` (media plus the id of the user who added it, null if unknown). With the session flag `fairQueue` (command `fairQueue/{true|false}`, `Update`/`FairQueue`, also in `Join`) `addMediaToQueue`, `addMediaListToQueue` and the REST `addpl` insert every media with `Queue.addFair` instead of at the end: the n-th queued media of a user goes behind the n-th of everyone else, and the user whose media is playing already had a turn. Only the new entry is placed, the existing queue is not reordered, except by `shuffle`, which with the flag rebuilds the queue in fair order (random per user, the users take turns); "play next"/"play now" always go to the front. The flag is off by default; `addpl` (`SessionController.addPlaylist`) switches it on when it fills an empty lobby with a playlist that begins with a song (video lobbies keep the plain order).
- Adding a command therefore requires: a `Command` subclass with its fields in `CommandJsonTest`, a `@MessageMapping` handler, its type in `session-command.ts` (also in `COMMAND_TYPES`/`UPDATE_TYPES` there), and a new `case` in `PlayerEngineService.processCommand` (the switches are exhaustive: the compiler reports a missing case).
- STOMP security: `WebSocketConfig` uses `@EnableWebSocketSecurity` with an `AuthorizationManager<Message<?>>` bean (`anyMessage().authenticated()`) and a no-op bean `csrfChannelInterceptor` (the client sends no CSRF token; other sites are kept out by the allowed origin of the endpoint and the SameSite cookie). `WebSocketAuthConfig` (order `HIGHEST_PRECEDENCE + 99`) registers the connection on CONNECT before the Spring Security interceptors (`+ 100`) run.
- Access control: `SessionMembershipInterceptor` drops every session command except `join` from users that are not members of the session. `join`/`leave`/`ready` take the user from the connection's `Principal` and reject a different `{userId}` in the destination.
- Errors: exceptions in handlers (`@MessageExceptionHandler`) and dropped commands are sent only to the sender as `ErrorCommand` on `/user/queue/errors`. The client shows them app-wide (`WsService.errors`, `AppComponent`); `WsService.publishSessionCommandWithResult` resolves to false if an error arrives within 1 s.
- The queue is only changed through the methods of `Queue`, inside `synchronized (session.getLock())`; the session user list is a `CopyOnWriteArrayList`. Every change counts up `Queue.version()`. A command that carries the queue or history (`SetMedia`, `Stop` at the end of the queue, `Join`, `Update` `Queue`/`History`/`QueueAndHistory`) is built from a `QueueSnapshot` taken under the same lock as the change and sends that version as `queueVersion`. Handlers run concurrently, so commands can reach the clients in another order than the changes happened: the client (`PlayerEngineService.applyQueue`) keeps a version for the queue and one for the history and drops older copies; its own `Join` always replaces both.
- Media sent by clients is resolved by id from the repository (`findMedia`); client-supplied media fields are not trusted.

### Synchronized start
- Changing media (`setMedia`) or jumping calls `SessionController.enterSyncState`, which starts a sync round (`SessionUserSynchronization`, with a round id) for the current media and schedules a 5 s timeout.
- The command that starts a round names it (`syncRound` in `SetMedia` and `Jump`; `Join` carries the running round, 0 if none). Clients load the media and send `ready/{userId}/{mediaId}/{position}/{round}` with that id on `canplaythrough` or `seeked`. The round and the media id are compared, not the position (browsers snap positions differently); ready messages outside a round or for an earlier round are ignored. The round id is what keeps the messages in order: handlers run concurrently, so without it the late ready of an earlier round for the same media ("Play now", then play right away) finished the new round and the `Start` could reach a client before the `SetMedia` it belongs to, which then cancelled that start. A client can only name a round after it got the command for it.
- When all session users are ready, or a user leaves and the rest are ready, or the timeout expires, the server sends `StartCommand` with an absolute epoch-millis start time (resume: `SYNC_DELAY` 500 ms ahead).
- Joining users get a `JoinCommand` with the session state (including `SYNC_*`), a start time `JOIN_DELAY` (3 s) in the future and the matching offset. The lobby requests the join (`SessionService.ensureJoined`, only if the session is not joined yet) and repeats it until its own `Join` arrives (`SessionService.requestJoin`); after a WebSocket reconnect the client joins again.
- `end/{mediaId}` is only accepted while playing and after `END_GRACE_PERIOD` (2 s), so late reports of slow clients do not skip the next media.
- Clock offset and latency (client `ClockSyncService`, NTP-like): a client tags small, fast commands with the STOMP header `sync-id`; `config/ClockSyncInterceptors` returns the tag plus `server-received`/`server-sent` on every message sent while handling the command. Samples also come from a burst of 10 pings to `/app/util/latency/{user}` (`UtilityController`) after every (re)connect. The offset of the shortest round trip within a 2 min window is used; offset changes shift the running playback anchor.
- Each client reports its playback status (`status/{userId}`: `IDLE`/`LOADING`/`READY`, latency, drift; `UserStatusService`, throttled) and the server broadcasts it as `Update`/`UserStatus` (in memory, per user: several tabs of one user overwrite each other). Shown in the listeners drawer of the full player.

### Client player
The playback of the session lives in the app-wide `PlayerEngineService` (`services/player-engine.service.ts`): the state of the session (`playerState`, `queue`, `history`, `sessionUsers`, ...), command handling and loading the media. Two parts have their own services, which the views do not use directly (the engine passes their state on): `PlaybackSyncService` knows when to play (the scheduled start, the playback anchor, drift correction; the engine calls `schedule` and, when the session stops playing at that position, `clear`), `MediaInfoService` what is shown about the current media (details, ratings, thumbnail sprite and chapters of the seek bar). It listens to the session topic as long as `SessionService.sessionId` is set, so the playback continues on every page; leaving the session (`SessionService.leaveSession`, also on logout) resets it and stops the media. `components/player/player.component.ts` is a thin abstract base class (display helpers, command shortcuts) of `RoomComponent` (the room, route `sessions/:sessionId/lobby`) and `MiniPlayerComponent` (footer of `AppComponent` on all pages but the lobby, login and register); both are pure views without subscriptions to media events. `MediaService` owns the audio **and** the video element: the video lives in a hidden host in `document.body` and is moved into the lobby with `attachVideo`/`detachVideo`, because a media element stops playing when it is removed from the document. Media can be `SONG` or `VIDEO` (`MediaType`; server uses JPA `JOINED` inheritance `Media` -> `Song`/`Video`). Spotify playback is delegated via `SpotifyDelegateComponent`/`SpotifyService` (Web Playback SDK) and server-side `spotify/SpotifyResource`.

- `PlaybackSyncService.schedule` starts at the scheduled client time; a late start is compensated by starting further into the media. It stores a playback anchor that `correctDrift` (on every `timeupdate`) compares with the actual position: small drift via `playbackRate` (±5 %), over 1 s by seeking. Pause/stop/SetMedia/Jump clear the anchor and cancel a start that is still pending.
- Hidden tabs without a user interaction do not load media at all (tabs with an interaction do, audio and video). Such a tab reports ready right away (`reportReadyIfUnableToLoad`), so the others do not wait for the sync timeout; it catches up via drift correction once the user returns.
- Autoplay: browsers block playback with sound until the user interacted with the page. `AutoplayService` detects this without playing (`getAutoplayPolicy` where available, else `navigator.userActivation`); while blocked the player plays muted and unmutes on the first interaction, showing a hint in the lobby. There is no join dialog.
- Subscriptions to `MediaService` events belong into `PlayerEngineService`, not into the view components. Opening the lobby of an already joined session must not join again: the `Join` reloads the media and interrupts the playback.

## Known issues
- After a server restart, session ids are reused, so clients reconnecting with an old session id can end up in a different session with the same id.
- `ws://`/`http://` are unencrypted: without the TLS proxy the password of a login and the login cookie can be read on the network.
- A WebSocket connection that is open stays logged in after its login ended (logout in another tab, changed password); it ends with the connection.
- The login has no limit of attempts.
