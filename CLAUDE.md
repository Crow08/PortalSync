# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

The repository root is the workspace; it is one git repository (GitHub `Crow08/PortalSync`) with two projects that together form one application (synchronized group listening/watching of music and video):

- `server/` — Spring Boot 4.1 (Spring 7, Jakarta EE 11, Jackson 3, Hibernate 7; Java 27 (Liberica Full 27 in `~/.jdks`, IntelliJ project SDK `liberica-full-27`), Maven, packaged as `war`), package `de.crow08.portalsync`
- `tools/` — PowerShell helpers that are not part of the build: `convert-video.ps1` (ffmpeg conversion, thumbnail sprites) and `start-caddy.ps1` (Caddy TLS proxy, uses `Caddyfile` in the repository root)
- `client/` — Angular 22 + Angular Material SPA, STOMP over WebSocket via `@stomp/rx-stomp` (own `RxStompService` in `services/rx-stomp.service.ts`)

Commit from the repository root; a change to the WebSocket protocol belongs into one commit touching both projects. `data.sql` (local seed) and `.idea/`, `.claude/` are git-ignored.

## Environment / profiles

The client environment file and the server profile must match, otherwise CORS and the WebSocket `setAllowedOrigins` check fail:

| Client config (`src/environments/`) | Server profile | Backend port |
|---|---|---|
| `environment.development.ts` (`development` configuration, `npm start`) | `dev` | 8081 |
| `environment.ts` (default, production builds, also the Docker image) | `prod` | 8080 (behind the TLS proxy: `https://`/`wss://` on 443) |

There is no `preprod` profile or client configuration any more (`environment.preprod.ts`, `application-preprod.properties`, the `preProd` configurations in `angular.json` and the `startPreProd` script are gone).

Server-side, `client.origin` (`prod`) or `client.host`/`client.port` (`dev`) define the single allowed origin (used in both `SecurityConfig.addCorsMappings` and `WebSocketConfig`). `client.storage-path` (`F:/media/` in `dev`, `MEDIA_PATH` in `prod`, **must end with a slash**) is the filesystem root of the media files.

`dev` and `prod` both use `ddl-auto=update` on a persistent database (`dev`: `music_stream_server` on the local XAMPP, `MYSQL_DATABASE` overrides it; `prod`: `portalsync`): **nothing is wiped on start and `data.sql` is not run automatically** (`spring.sql.init.mode` is not set). Never drop the database to "reset" it; it holds the real library. `src/main/resources/data.sql` is only a local seed for an *empty* database (users 1–5, media 1–29, playlists 1–4, user 1 `admin`). It is **git-ignored** (real user names and password hashes, personal library) and not in a fresh clone; the README describes creating the first admin by SQL. If it exists, load it by hand, e.g. `C:\xampp\mysql\bin\mysql.exe -u root --default-character-set=utf8mb4 music_stream_server -e "source src/main/resources/data.sql"` after the server created the tables. Hibernate has to create the schema first; `playlist_owner` stays empty until the next server start (`PlaylistOwnerMigration` makes the authors the owners). In the seed, playlist 4 ("Bleach", media 1–29) references files under `F:/media/videos/`; other media may not exist.

`src/main/resources/static/` contains a copy of the client build (hashed bundles) that the server serves itself (`SecurityConfig`: `ClientResourceResolver`; paths without a file extension, except `/api` and `/ws`, get `index.html` for the client router). It is not rebuilt automatically — run `npm run buildServer` in the client.

HTTPS (prod): `Caddyfile` (repository root) runs Caddy as TLS proxy for the host name in the environment variable `PORTALSYNC_DOMAIN` (required) and forwards everything to the server (`localhost:8080`, `PORTALSYNC_UPSTREAM` overrides). One origin: `environment.ts` takes `window.location.origin` for `dbServer`, `frontendServer` and `wsServer` (ws/wss derived), so the production build contains no host name and works on every domain, but only when the server serves the client itself. The `prod` profile therefore takes `client.origin` from the environment variable `CLIENT_ORIGIN` (default `http://localhost:8080`, the only origin allowed for CORS and the WebSocket; e.g. `https://portalsync.example.org`; other prod variables: `SERVER_PORT`, `MYSQL_HOST`/`MYSQL_DATABASE`/`MYSQL_USER`/`MYSQL_PASSWORD`, `MEDIA_PATH`, `URLCRYPTO_SECRET`, `SPOTIFY_*`; the Spotify redirect defaults to `CLIENT_ORIGIN/spotify/redirect`) and `server.forward-headers-strategy=framework` (Spring has to see `https`, otherwise the CORS check treats same-origin requests as foreign). Caddy: the single binary of the official release (https://github.com/caddyserver/caddy/releases, `caddy_<version>_windows_amd64.zip`, check the SHA-512 from the checksum file) lies in `D:\Programs\caddy\caddy.exe`, not in the project. Start it with `tools\start-caddy.ps1` (`-Detached` runs it hidden with the log in `%TEMP%\caddy.log`, `-Stop` stops it; `caddy.exe` is looked up in `CADDY_EXE`, that path and the PATH). The script stops when port 80 or 443 is in use, by any other web server. Caddy obtains and renews the certificate itself and stores it in `%APPDATA%\Caddy` (add `acme_ca https://acme-staging-v02.api.letsencrypt.org/directory` in a global block of the Caddyfile for tests: staging has no rate limits but browsers do not trust it). It does not run as a service by itself. Spotify's redirect URI has to match `spotify.client.redirect` exactly and has to be HTTPS (except loopback IPs, `localhost` is not allowed).

Docker (`compose.yaml`, `Dockerfile`, `.dockerignore`, `.env.example` in the repository root): `cp .env.example .env`, set `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD` and `URLCRYPTO_SECRET` (required, no default), then `docker compose up -d --build` in the repository root (app on `127.0.0.1:8080`, `APP_BIND`/`APP_PORT` change that; `docker compose --profile tls up -d` adds Caddy on 80/443 for `PORTALSYNC_DOMAIN`). Services: `db` (MySQL 8.4, volume `db-data`; unlike the local XAMPP MariaDB 10.4 it needs no Hibernate workarounds and logs no DDL warnings), `app` (client + server in one image, Spring profile `prod` = `application-prod.properties`, everything from the environment: `MYSQL_*`, `CLIENT_ORIGIN` = the only allowed origin, `URLCRYPTO_SECRET`, `SPOTIFY_*`, `MEDIA_PATH`) and optional `caddy`. The build context is the repository root (both projects side by side), the Dockerfile builds the client with the normal `production` configuration (`environment.ts`: everything on `window.location.origin`, so the image is independent of the host name) and replaces `static/` in the server sources with it; `.dockerignore` is an allow list. The media library is a bind mount (`MEDIA_DIR`, default `./media`, e.g. `F:/media`) at `/media`; the app runs as uid 10001 and must be able to write there (uploads). The database starts empty: users come from the invite flow or from loading `data.sql` by hand (`docker compose exec -T db mysql -u root -p... portalsync < server/src/main/resources/data.sql`); to move the existing library, `mysqldump` the XAMPP database and load it the same way. Only compose-time variables of services in a profile need defaults (`${PORTALSYNC_DOMAIN:-localhost}`), a `:?` there would break every `up`. Verified: build, healthy stack, login, signed media with range requests, thumbnails, STOMP over ws, and the `tls` profile with `localhost`.

Secrets: the Spotify client id and secret come from the environment (`SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET`, set in the IntelliJ run configuration). The committed url-crypto key (`Not#So%Secret`) and the unset DB password in `application-*.properties` are intentional development defaults; production must override them.

## Architecture

### Two communication channels
1. **REST** (`/api/**`, HTTP Basic auth, CSRF disabled): CRUD for the JPA entities in `model/*` (each package has `Entity`, `Repository`, `Resource` = REST controller). Client side: `services/*.service.ts`, auth headers from `AuthenticationService`. `User.password` is write only (never serialized).
2. **STOMP over WebSocket** (endpoint `/ws`): all live session/playback control. Credentials and the session id are passed as STOMP CONNECT headers `login`, `usercode`, `session` (see `WsConfigService.configParameter`), validated in `WebSocketAuthConfig.WebSocketAuthInterceptor` -> `WebSocketSessionController.authenticateNewConnection`. `/ws/**` is excluded from HTTP security.

### Media file serving
`/api/v1/media/data/{mediaId}` is a custom resource handler in `SecurityConfig.addResourceHandlers`: it looks up the `Media` entity by id and resolves its `uri` against `client.storage-path` only (Spring 7 rejects the former `classpath:/` location). These URLs are signed via neverpile `url-crypto-kit` 2.x (pre-signed URLs, `psuEnabledPathPatterns`; an authenticated `GET .../media/data/{id}?X-NPE-PSU-Duration=PT1H` returns the signed URL as plain text, see `PlayerEngineService`), so the browser `<audio>/<video>` element can load them without Basic auth headers. Seeking uses HTTP range requests on progressive MP4 (no DASH); videos need the `moov` atom at the front (fast start). New videos (e.g. MKV with ASS subtitles, 10-bit H.264) are converted with `tools/convert-video.ps1` (ffmpeg): 8-bit H.264 + AAC, subtitles burned in, fast start; `Get-Help .\tools\convert-video.ps1 -Full` for options. The script is not part of the build.

`/api/v1/media/thumbnails/{mediaId}` (same resolver, also pre-signed) serves the seek bar preview sprite of a video: `<video uri without extension>.thumbs.jpg` next to the video, written by `convert-video.ps1` (`-ThumbnailsOnly` for existing videos). Sprite format: one 160x90 tile every 2 s, 10 tiles per row, row-major; the constants are duplicated in `convert-video.ps1` and `player-track.component.ts`. Thumbnails are optional: without a sprite (songs, 404) the seek bar shows no preview.

Chapters: `convert-video.ps1` keeps the source chapters in the MP4 (`-map_chapters 0`, ffmpeg writes a Nero `moov/udta/chpl` box). Browsers do not expose MP4 chapters, so `GET /api/v1/media/video/{id}/chapters` (Basic auth, `utils/Mp4ChapterReader`) parses that box and returns `[{start, title}]` (start in seconds, empty list without chapters). The seek bar shows chapter boundaries as gaps and the chapter title in the hover preview.

### Playlist ownership
A `Playlist` has a list of `owners` (table `playlist_owner`; `author` is only the creator and the first owner) and a flag `publicOwnership`. Owners and admins change the songs (`addSongToPlaylist`, `addSongsToPlaylist`, `removeSongsFromPlaylist`, upload and import into a playlist) and manage the owners (`PUT`/`DELETE /api/v1/playlists/{id}/owners/{userId}`, the last owner can not be removed) and the flag (`PUT .../public/{true|false}`); with `publicOwnership` everybody changes the songs, but only owners and admins manage owners and flag. For everyone else a playlist is read only (403). The rules live in `PlaylistAccess`, the client mirrors them in `Playlist.canEdit`/`canManage` to hide controls. `PlaylistOwnerMigration` makes the author the owner of playlists without owners at every start (existing databases). `GET /api/v1/users/all` lists id and name of all users, `GET /api/v1/playlists/{id}/media` the media of a playlist.

### Sessions (in-memory, not persisted)
`sessions/SessionRepository` is a plain `HashMap` — sessions, their `Queue` (queued + history + current media) and connected users are lost on server restart, and session ids start at 1 again. `SessionController` holds the playback state machine (`Session.SessionState`: `PLAY, STOP, PAUSE, SYNC_PLAY, SYNC_STOP, SYNC_PAUSE`) and timing (`mediaStarted`, `savedProgression`).

Deleting: `DELETE /api/v1/sessions/{id}` (`SessionResource`) is allowed for the creator (`Session.creatorId`) and admins (`User.admin`, a DB-only flag, in the dev seed user 1). `SessionController.deleteSession` removes the session and broadcasts `SessionDeleted`; the client (`PlayerEngineService`) then resets locally via `SessionService.sessionDeleted` and goes to the session list.

`WebSocketSessionController` tracks which music sessions each WebSocket connection joined (via `join` or the CONNECT `session` header). A user is only removed from a session when no other connection of that user is still in it.

### Playback command protocol
- Client publishes to `/app/sessions/{sessionId}/commands/{name}[/{params}]` (`WsService.publishSessionCommand`); handlers are the `@MessageMapping` methods in `wscommunication/PlayerControlsController`.
- Each handler returns a `Command` subclass (`wscommunication/commands/`) broadcast to `/topic/sessions/{sessionId}`. The JSON `type` field (e.g. `Start`, `SetMedia`, `Join`, `Update` with sub-types `Queue`/`History`/`QueueAndHistory`/`LoopMode`) is dispatched in the client's `PlayerEngineService.processCommand` `switch (commandObject.type)`.
- Commands addressing a queue entry (`skipTo`, `movedMedia`, `deleteMediaFromQueue`) send the index in the combined list (history, current, queue) plus the media id; the server picks the occurrence of the id nearest to the index (`findInHistoryAndQueue`) and rejects the command if the media is gone.
- `SetMedia` carries the complete queue and history; the client replaces its state with them instead of deriving it from the media id (media can occur several times). When the queue ends, the server stops the session and sends `Stop` with the queue and history (no current media); a plain `Stop` has neither.
- Adding a command therefore requires: a `Command` subclass, a `@MessageMapping` handler, and a new `case` in `PlayerEngineService.processCommand`.
- STOMP security: `WebSocketConfig` uses `@EnableWebSocketSecurity` with an `AuthorizationManager<Message<?>>` bean (`anyMessage().authenticated()`) and a no-op bean `csrfChannelInterceptor` (the client is served from another origin and sends no CSRF token). `WebSocketAuthConfig` (order `HIGHEST_PRECEDENCE + 99`) sets the user on CONNECT before the Spring Security interceptors (`+ 100`) run.
- Access control: `SessionMembershipInterceptor` drops every session command except `join` from users that are not members of the session. `join`/`leave`/`ready` take the user from the connection's `Principal` and reject a different `{userId}` in the destination.
- Errors: exceptions in handlers (`@MessageExceptionHandler`) and dropped commands are sent only to the sender as `ErrorCommand` on `/user/queue/errors`. The client shows them app-wide (`WsService.errors`, `AppComponent`); `WsService.publishSessionCommandWithResult` resolves to false if an error arrives within 1 s.
- Queue mutations must be done inside `synchronized (session.getQueue())`; the session user list is a `CopyOnWriteArrayList`.
- Media sent by clients is resolved by id from the repository (`findMedia`); client-supplied media fields are not trusted.

### Synchronized start
- Changing media (`setMedia`) or jumping calls `SessionController.enterSyncState`, which starts a sync round (`SessionUserSynchronization`, with a round id) for the current media and schedules a 5 s timeout.
- Clients load the media and send `ready/{userId}/{mediaId}/{position}` on `canplaythrough` or `seeked`. Only the media id is compared (browsers snap positions differently); ready messages outside a round are ignored.
- When all session users are ready, or a user leaves and the rest are ready, or the timeout expires, the server sends `StartCommand` with an absolute epoch-millis start time (resume: `SYNC_DELAY` 500 ms ahead).
- Joining users get a `JoinCommand` with the session state (including `SYNC_*`), a start time `JOIN_DELAY` (3 s) in the future and the matching offset. The lobby requests the join (`SessionService.ensureJoined`, only if the session is not joined yet) and repeats it until its own `Join` arrives (`SessionService.requestJoin`); after a WebSocket reconnect the client joins again.
- `end/{mediaId}` is only accepted while playing and after `END_GRACE_PERIOD` (2 s), so late reports of slow clients do not skip the next media.
- Clock offset and latency (client `ClockSyncService`, NTP-like): a client tags small, fast commands with the STOMP header `sync-id`; `config/ClockSyncInterceptors` returns the tag plus `server-received`/`server-sent` on every message sent while handling the command. Samples also come from a burst of 10 pings to `/app/util/latency/{user}` (`UtilityController`) after every (re)connect. The offset of the shortest round trip within a 2 min window is used; offset changes shift the running playback anchor.
- Each client reports its playback status (`status/{userId}`: `IDLE`/`LOADING`/`READY`, latency, drift; `UserStatusService`, throttled) and the server broadcasts it as `Update`/`UserStatus` (in memory, per user: several tabs of one user overwrite each other). Shown in the listeners drawer of the full player.

### Client player
The playback of the session lives in the app-wide `PlayerEngineService` (`services/player-engine.service.ts`): the player state (`playerState`, `queue`, `history`, `currentMedia`, `sessionUsers`, ...), command handling, sync and drift correction. It listens to the session topic as long as `SessionService.sessionId` is set, so the playback continues on every page; leaving the session (`SessionService.leaveSession`, also on logout) resets it and stops the media. `components/player/player.component.ts` is a thin abstract base class (display helpers, command shortcuts) of `RoomComponent` (the room, route `sessions/:sessionId/lobby`) and `MiniPlayerComponent` (footer of `AppComponent` on all pages but the lobby, login and register); both are pure views without subscriptions to media events. `MediaService` owns the audio **and** the video element: the video lives in a hidden host in `document.body` and is moved into the lobby with `attachVideo`/`detachVideo`, because a media element stops playing when it is removed from the document. Media can be `SONG` or `VIDEO` (`MediaType`; server uses JPA `JOINED` inheritance `Media` -> `Song`/`Video`). Spotify playback is delegated via `SpotifyDelegateComponent`/`SpotifyService` (Web Playback SDK) and server-side `spotify/SpotifyResource`.

- `schedulePlay` (engine) starts at the scheduled client time; a late start is compensated by starting further into the media. It stores a playback anchor that `correctDrift` (on every `timeupdate`) compares with the actual position: small drift via `playbackRate` (±5 %), over 1 s by seeking. Pause/stop/SetMedia/Jump clear the anchor.
- Hidden tabs without a user interaction do not load media at all (tabs with an interaction do, audio and video). Such a tab reports ready right away (`reportReadyIfUnableToLoad`), so the others do not wait for the sync timeout; it catches up via drift correction once the user returns.
- Autoplay: browsers block playback with sound until the user interacted with the page. `AutoplayService` detects this without playing (`getAutoplayPolicy` where available, else `navigator.userActivation`); while blocked the player plays muted and unmutes on the first interaction, showing a hint in the lobby. There is no join dialog.
- Subscriptions to `MediaService` events belong into `PlayerEngineService`, not into the view components. Opening the lobby of an already joined session must not join again: the `Join` reloads the media and interrupts the playback.

Design: one dark Material base theme, `graphite`, in several color themes chosen in the settings (`SettingsService.theme`, `msc_theme`, default `ocean`; ocean, mint, violet, amber, mono = grayscale). The themes are defined once in `src/app/themes/themes.scss` (accent, ink, surfaces, text, glow, video/song colors, Material scale; the values were generated in OKLCH from the accent, the surfaces share its hue with very low chroma). `theme.scss` turns every entry into `.graphite-theme.theme-<id>` (the `--ps-*` variables plus the Material color scheme, colors only; the default theme carries typography and density); `AppComponent.themeClass` sets the classes on `#app-theme-container` and `ThemeAwareOverlayContainer` copies `graphite-theme` and `theme-*` to the Material overlays. The `:root` values in `styles.scss` are the default theme. To add a theme: one entry in `themes.scss` and one in `THEMES` in `settings.service.ts` (the colors there only draw the choice). Non-Material components use `--ps-*`, never hex values (`--ps-glow`, `color-mix` with `--ps-bg` for scrims); the logo (`src/assets/logo.svg`, `favicon.ico` is rendered from it) and `logo-scene.svg` keep fixed colors. Only dark schemes exist: a light theme would need the hardcoded white text and `rgba(255,…)` overlays reworked. Shared colors and fonts are CSS variables `--ps-*` (`src/styles.scss`). Theme colors for non-Material elements that need the palette go into the `app-colors` mixin in `src/theme.scss`. App shell (`AppComponent`): header with account menu, navigation rail on the left (bottom bar below 720 px), page content, mini player as footer; login and register hide header and rail (`auth-page`). Background pictures are optional and git-ignored (origin and license unknown): `src/assets/backgrounds/` with a `backgrounds.json` list (see the README there), loaded at runtime by `SettingsService`; they lie behind all pages except the player (`#content` under a dark layer, see `styles.scss`; the app shell sets `--ps-bg-image`), chosen in the settings (`SettingsService.background`, default the first picture, `none` = the gradient of the theme, shown as "Gradient"; without `backgrounds.json` the setting is hidden). Naming in the UI: a session is a "lobby" (the list of lobbies is the start page, nav entry "Lobbies") and the page with the playback is the "Player" (nav entry "Player", route `sessions/:sessionId/lobby`); code and routes keep the old names. Pages: lobbies (`HomeComponent` at `/`: lobby list, create lobby, invite), library (`/library`, loads all media once; search, filter and sort happen in the client; the list is a virtual scroll list with rows of 56 px), settings, upload, Spotify import, room (lobby).

## Known issues
- After a server restart, session ids are reused, so clients reconnecting with an old session id can end up in a different session with the same id.
- The client stores the password in `localStorage` and sends it as a WebSocket header; `ws://`/`http://` are unencrypted.
